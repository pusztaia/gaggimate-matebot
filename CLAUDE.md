# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This is a **deployment/config repo**, not an application codebase. It documents and generates the Portainer/Docker Compose stack that runs a companion bot for a [GaggiMate](https://github.com/jniebuhr/gaggimate) espresso machine controller on a Raspberry Pi 4. The bot is [`ghcr.io/alexnly/matebot`](https://github.com/alexnly/matebot) as its upstream base, but the **active deployed image is a locally built overlay** on top of it (see below) — not the stock image pulled from a registry. There is no build system, package manager, or test runner at the top level — the "product" is a handful of YAML/env/shell files plus a static HTML configurator.

Three logically separate things live here:

1. **The active production stack** (repo root): `12-matebot.yaml`, `portainer.env.example`, `prepare-matebot.sh`, `prepare-matebot-telegram.sh`, `README.md`. These describe the currently deployed, intentionally minimal configuration — but "minimal" refers to scope (no archive/journal sync), not to the image: it already includes Telegram profile control, `/doctor` diagnostics, and thermal-overshoot-aware "ready" detection, all sourced from `matebot_extension/matebot-doctor-ready-exact/` (point 3 below). `12-matebot.yaml` builds/references that image with `pull_policy: never`, so it must be built on the Docker host before the stack can start.
2. **`index.html`** — a standalone, client-side (no backend) GitHub Pages configurator that generates the same files above (`12-matebot.yaml`, `portainer.env`, `prepare-matebot.sh`, `prepare-matebot-telegram.sh`, `INSTALL.generated.md`) from a handful of user inputs (GaggiMate host, timezone, base dir, secrets dir). All other values (UID/GID, resource limits, image tag, feature flags) are hard-coded inside it. **When updating any default/fixed value in the root config files, update the matching literal inside `index.html`'s generator too — they must stay in sync**, since the page is the distribution mechanism for new deployments.
3. **`matebot_extension/`** — the source of the deployed image: a Docker image *overlay* that patches the upstream `matebot` 0.4.0 package to add the features described above. It contains a single directory, `matebot-doctor-ready-exact/`, which has its own `CLAUDE.md` at `matebot_extension/matebot-doctor-ready-exact/CLAUDE.md` — read that before working on the overlay's Python source or Dockerfile. (Earlier/superseded patch-kit iterations and an unmodified upstream 0.4.0 snapshot used to live alongside it as sibling directories; they were removed as unused once `matebot-doctor-ready-exact/` became the only overlay the root stack references — if you ever need to re-diff against a fresh upstream `matebot` release, re-pull the source from a running `ghcr.io/alexnly/matebot` container rather than looking for a baseline copy here.)

## Core design principle (root stack)

Keep the live workflow simple: **shot data stays on GaggiMate; only MATEbot's small state directory is persisted on the Pi.** The active `12-matebot.yaml` deliberately omits `MATEBOT_DATA_REPO`, so there is no shot archive, journal sync, or `.slog`/JSON export running on the Pi — those are documented as optional/disabled features (see `README.md` §13). Do not add `MATEBOT_DATA_REPO` or archive-related env/volumes to the active stack without explicit instruction; this was a deliberate scope reduction, and re-enabling it was previously tied to a failure mode (`README.md` §12.3, "machine went offline before the journal could sync").

## Key architecture facts

- **Communication path**: Telegram (user) ↔ MATEbot (container on RBP4) ↔ WebSocket `ws://<gaggimate-host>/ws` ↔ GaggiMate display firmware ↔ Bluetooth ↔ GaggiMate controller board/hardware. MATEbot listens for `evt:status` events to detect a finished shot, then writes the post-shot questionnaire answers back via `req:history:notes:save` — it does not maintain its own shot history.
- **Image**: `12-matebot.yaml` sets `image: matebot-profile-control:0.4.0-doctor-ready1` with `pull_policy: never`. This is built locally with `docker build -f Dockerfile.profile-control ...` from `matebot_extension/matebot-doctor-ready-exact/package/` (`FROM ghcr.io/alexnly/matebot:latest`, version-pinned to exactly `0.4.0`, patched files copied in) — the Docker host must build it before deploying the stack. Diun is disabled (`diun.enable: "false"`) for this image since it can't check a registry for a local build.
- **Secrets**: the Telegram bot token is never stored in YAML/env in this repo. `12-matebot.yaml`'s entrypoint reads `/run/secrets/telegram_token` (plain text) and `/run/secrets/telegram_chat_id` (a single plain numeric chat id, optionally negative — validated with a shell `case` statement at container startup, not parsed as JSON). These are MATEbot-dedicated secret files, not shared with a Diun deployment's JSON-array secrets. Both are bind-mounted read-only from host paths (default `/mnt/ssd/secrets/...`), owned by the container's `uid=1000/gid=1000` user with mode `640`/dir `750` (see `README.md` §6.1 for exact commands).
- **`MATEBOT_IGNORE_PROFILES`** is a configurable env var (default `(?i)backflush|descale|flush|clean`) that filters cleaning/maintenance profiles out of the post-shot questionnaire — it's not hard-coded.
- **`index.html` configurator** only collects: GaggiMate host, timezone, MATEbot base directory, Telegram secrets directory. It never asks for the bot token — `prepare-matebot-telegram.sh` prompts for that interactively on the Pi with echo disabled. Everything else generated (resource limits, `MATEBOT_HINTS=1`, `MATEBOT_MIN_SHOT_S=10`, image tag, `MATEBOT_IGNORE_PROFILES`) is fixed; treat those as the current production defaults when reasoning about behavior.
- **`prepare-matebot.sh`** at the repo root only creates the `state/` directory the active stack needs — it does not create `shots/`/`json/` archive directories or git-init anything. Those would belong to the disabled archive feature (README §13) if ever added; don't assume they exist.

## Common tasks

There is no build/lint/test command for the root-level files — they're plain YAML/shell/HTML, validated by manual deployment (`docker compose config`, or deploying via Portainer) and code review against `README.md`, which is the authoritative spec for current behavior. When changing behavior described in `README.md` (env var defaults, file paths, filtering thresholds, Telegram command list), update `README.md` in the same change — it is treated as living documentation of the actual deployed system, not a static intro.

For work inside `matebot_extension/matebot-doctor-ready-exact/package/`, see that directory's own `CLAUDE.md` for the test command (`python3 -m pytest tests/`), Docker build/smoke-test commands, and the overlay's internal architecture (`warmup.py` thermal state machine, `profiles.py` profile control, `diagnostics.py` `/doctor` checks, `machine.py` WebSocket client quirks).
